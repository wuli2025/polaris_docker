# 完成前验证（证据门）

铁律：**没有新鲜的验证证据，不许宣称「完成 / 修好 / 测试通过」**。虚报完成是信任杀手。源自 superpowers 的 verification-before-completion。

## 五步门（每次宣称前走一遍）
1. **IDENTIFY**：这个论断用什么命令能证明？（构建 = 构建命令；修复 = 复现路径；测试过 = 跑测试）
2. **RUN**：现在完整跑一遍。不用上次的输出、不用缓存记忆、不「刚才跑过了」。
3. **READ**：读完整输出 + 退出码，数清失败数，别只瞄最后一行。
4. **VERIFY**：输出真的支持论断吗？「编译过」≠「功能对」；lint 绿 ≠ build 绿。
5. 四步全过，才许开口宣称。**跳过任何一步 = 撒谎，不是验证。**

## 红线
- 宣称前禁用「应该 / 大概 / 看起来 / probably / should」——有这些词说明你没验证。
- 回归修复必须展示**红 → 绿全程**：先跑复现确认还是坏的？不对，是先有失败证据再有修复后通过证据，两头都要。
- 声称「N 项需求都实现了」→ 逐条 checklist 核对，一条一证据。
- 子任务 / 子 agent 自报的「完成」不可信：独立看 `git diff` / 实际产物核实。
- 有一项验证是红的就如实说红，不许「基本上没问题」。

## 输出格式
- 宣称时附上证据：跑了什么命令、关键输出几行、退出码。让对方不用追问就能核实。
