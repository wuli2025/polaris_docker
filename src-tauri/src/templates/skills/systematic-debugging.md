# 系统化调试（根因四阶段）

修 bug 的铁律：**没查到根因不许动手修**。「看着像 X，改一下试试」的症状修补 = 失败。源自 superpowers 的 systematic-debugging 方法论。

## Phase 1 · 根因调查
- 完整读错误信息和堆栈，一个字不跳（答案常就写在里面）。
- 稳定复现：写下精确触发步骤，复现不了就先搞复现，不许盲修。
- 查最近改动：`git diff` / `git log`、新加的依赖、改过的配置。
- 多组件系统在**每个组件边界**打点取证（进什么、出什么），沿调用栈**反向追踪坏值的起源**——日志报在 A 不代表错在 A。

## Phase 2 · 模式对比
- 在代码库里找一段「干同样事且能跑」的相似代码，与坏代码逐项对比：依赖版本、配置、调用方式、隐含假设，差异点就是嫌疑人。

## Phase 3 · 假设验证
- 形成**单一具体假设**：「X 是根因，因为 Y」。说不出这句话就回 Phase 1。
- 用最小改动验证假设，**一次只动一个变量**；不成立就换假设，不许叠加乱改。

## Phase 4 · 修复与固化
- 先写一个能复现此 bug 的失败测试（固化它），再做针对根因的单一修复。
- 跑该测试转绿 + 跑周边测试确认无回归，才算修完。

## 红线
- 以下念头出现 = 立刻回 Phase 1：「先快速修一下回头再查」「就改改 X 试试」「同时改几处碰运气」。
- 吞异常、调大超时、加重试来压症状，不算修。
- **连续 3 次修复失败 → 停下质疑架构和最初假设**，不许盲修第四次。
