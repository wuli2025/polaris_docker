# Bug 复现与回归

QA 视角处理一个 bug 的完整闭环：**复现 → 最小化 → 报告 → 回归固化**。没有复现步骤的 bug 报告等于没报。

## 1 · 复现
- 从用户描述提取：环境（版本 / 系统 / 浏览器）、操作序列、预期 vs 实际。
- 实际执行这套步骤。复现不出来时逐个排查变量：账号 / 数据状态 / 时序 / 缓存 / 并发，记录每次尝试的差异。
- 概率性 bug：写脚本循环跑，量化复现率（如 100 次中 7 次），别用「偶尔」。

## 2 · 最小化
- 逐步删减操作和数据，找到**仍能触发的最小步骤集**——通常从 15 步缩到 3-4 步，根因方向也随之显形。
- 二分法定位引入点：`git bisect`（能跑的话）或按版本二分安装验证。

## 3 · 报告（固定结构）
- **标题**：一句话 = 现象 + 触发条件（「导出超过 1 万行时 CSV 乱码」，不是「导出有问题」）。
- **环境** / **最小复现步骤**（编号，逐步可执行）/ **预期结果** / **实际结果**（截图、日志、错误码原文）/ **复现率** / **严重级**（阻断 / 严重 / 一般 / 轻微）+ 影响面一句话。
- 有线索时附「疑似根因」，但明确标注是推测。

## 4 · 回归固化
- bug 修复后：先按最小步骤验证真修了，再把复现步骤转成自动化回归用例（能自动化的必须自动化），挂进回归套件。
- 回归用例断言的是**这个 bug 的具体现象**，不是泛泛的功能可用。

## 红线
- 复现不了就标「无法复现 + 已尝试的变量清单」，不许凭想象写报告。
- 一个报告一个 bug，别打包。
