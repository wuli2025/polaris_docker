# 实施计划编写

接到多步开发任务、要先出计划再动手时用。核心假设：**执行者对代码库零上下文**——计划必须自足到「照着打字就能干」。源自 superpowers 的 writing-plans。

## 计划结构
1. 头部固定四段：**Goal** 一句话 / **Architecture** 2-3 句 / **Tech Stack** / **全局约束**（带精确值：超时多少毫秒、上限多少条，不许写「合理值」）。
2. 先画文件结构图：每个文件单一职责、小到能整个装进上下文、按职责而非技术层分组；再往下拆任务。
3. 每个任务 = 一个可独立评审的交付物；每一步 = 2-5 分钟工作量，含：精确文件路径、完整代码（不是伪码）、可直接运行的验证命令。
4. 每步固定节奏：写失败测试 → 跑（确认红）→ 实现 → 跑（确认绿）→ commit。

## 红线
- **禁止占位词**：「TBD」「处理边界情况」「类似任务 N」「等等」——出现即返工。
- 跨任务引用的函数名 / 签名 / 参数类型必须**逐字一致**，执行者不会帮你猜。
- 不为「以后可能用到」加任务；YAGNI，无情砍范围，列「明确不做」清单。

## 自审四查（写完必过）
1. 需求逐条能追溯到某个任务，无孤儿需求。
2. 全文扫一遍占位词。
3. 跨任务类型 / 命名一致性。
4. 空缺补齐：漏了迁移？漏了回滚？漏了错误路径？

## 落盘
- 存到项目 `docs/plans/YYYY-MM-DD-<feature>.md`（或用户指定处），交付路径而非贴全文。
